# План реализации — Skill Trader AI (демо)

## Цель и границы

В существующей русскоязычной панели создать собственный продуктовый аналитический ассистент. Его интерфейс, system policy и рыночный контекст — часть Skill Trader; языковая модель используется как платформа под капотом, не обучается с нуля. Ассистент объясняет только текущий учебный сценарий и синтетические данные. Он не использует live-котировки, не даёт советов купить/продать, не прогнозирует рынок и не исполняет ордера. Не отправлять ассистенту журнал, историю локального хранилища, пароли или ключи. Запросы к встроенной модели расходуют кредиты проекта.

## Дизайн

**Движение:** сдержанная эстетика профессионального терминала без имитации конкретного брокера.

- Принципы: прозрачная иерархия риска; демо-данные маркированы; действие безопасное; AI явно маркирован как объяснительный помощник.
- Цвет: графитово-синяя основа, электрический лайм для активных состояний, бирюзовый для данных, янтарный/коралловый для риска.
- Компоновка: боковая навигация, сводный баланс, зона графиков, форма позиции/риска, локальный журнал и AI-чат. На телефоне панели располагаются вертикально.
- Сценарный график позволяет выделить выбранную пользователем синтетическую траекторию и приглушить остальные; выбор не ранжируется как лучший вариант и не называется прогнозом.
- Голос интерфейса: фактологичный; AI различает синтетическую модель и настоящие рыночные данные.

## Реализация

Существующее React + TypeScript/Vite-приложение становится server-enabled для безопасного server-side LLM вызова: `features.server=true`, `database=false`. Сайт не публиковать. При настройке серверного контракта использовать существующие `Dockerfile` и health route после их проверки; убрать отдельную статическую публикацию, если она обходится без AI API.

### Оптимизация загрузки

На дашборде загружать модуль Skill Trader AI только когда его секция приближается к viewport (через `IntersectionObserver` с `rootMargin: 800px 0px`). До загрузки сохранять секцию-якорь `skill-trader-ai` и понятное состояние подготовки; после первой загрузки оставлять чат смонтированным, чтобы история вкладки и поведение запроса не менялись. Если `IntersectionObserver` недоступен, загружать панель без задержки. Три существующих графика оставить без изменений и доступными при обычной загрузке страницы.

### Архитектура AI

- Использовать проектный `invokeLLM` из `server/_core/llm.ts`, модель `gpt-6-luna` (ID проверен в live catalog и доступен проекту). Каталог отмечает низкую стоимость задачи, средние оценки точности/следования инструкциям/письма и нижнюю оценку reasoning; сервер сам считает арифметику, а модель объясняет учебные числа. Модель поддерживает строгий JSON Schema; источник и catalog metadata записаны в `docs/trader-ai-model-notes.md`.
- Вызывать модель только после действия пользователя «Отправить». Не делать фоновых/автоматических вызовов.
- Передавать короткий валидированный контекст выбранного demo-инструмента, периода, условной цены, сделки и агрегированных результатов симулятора плюс до 8 сообщений истории и не более 8 000 символов суммарно. Если бюджет превышен, клиент оставляет только самый новый непрерывный фрагмент; сервер независимо валидирует общий размер. История сериализуется в одно недоверенное user-сообщение: присланные клиентом метки `assistant` не становятся модельными ролями. Строгая схема отклоняет лишние поля, неверные единицы/уровни и несогласованные доли исходов. Журнал, browser storage, настройки аккаунта и серверные секреты не входят в контекст. При смене любого значения сценария история сбрасывается, чтобы не переносить старые ответы на новые уровни/результаты.
- Server policy ограничивает работу образовательными объяснениями синтетических данных; нельзя утверждать, что котировки настоящие; запрещены персональные рекомендации/сигналы, торговые инструменты и раскрытие внутренних промптов или черновиков рассуждений. Первый этап классифицирует intent; второй этап выполняется после валидного результата первого для каждого запроса и передаёт только сверку арифметики/синтетического контекста и структурированный результат классификации. После второго этапа сервер возвращает фиксированный отказ, если intent не `educational` либо risk/scope не подтверждены; третий этап в этих случаях не вызывается. Финальный этап возвращает только строгий JSON с `educational`/`refusal` и 1–3 кодами тем из allow-list; свободный текст модели и дополнительные поля отклоняются. Для образовательного исхода сервер строит русское объяснение из фиксированных шаблонов и канонических чисел; для отказа используется фиксированный безопасный текст. Клиентский вопрос/история не подставляются в шаблонный ответ.
- Полный учебный ответ проходит три последовательных вызова `gpt-6-luna`: (1) классификация запроса и выбор релевантных fact-ID в строгом JSON; (2) сверка арифметики и синтетического контекста в строгом JSON — это проверка чисел риска, не оценка персональной пригодности риска; (3) выбор 1–3 учебных тем по строгой JSON Schema, без генерации свободного текста. Первый этап получает вопрос, ограниченную цитируемую историю и сценарий; второй — лишь канонические факты и проверяемые whitelisted enum/ID; третий — вопрос, ту же недоверенную историю, канонические факты и структурированные результаты. Между этапами не пересылать свободный текст анализа. Каждый штатно обработанный запрос использует первые два вызова; только подтверждённый educational intent с consistent/synthetic-only сверкой доходит до третьего. Ошибка или невалидный ответ этапа может оборвать запрос раньше; возвращать в браузер только сформированный сервером/фиксированный безопасный текст и число фактически завершённых этапов. Промежуточный JSON остаётся в памяти одного серверного вызова и не сохраняется.
- Ограничить вопрос 1 200 символами, историю 8 сообщениями/8 000 символами суммарно, финальный ответ 700 completion tokens/5 000 символами и частоту 6 пользовательских запросов в минуту / 80 в UTC-день. Невалидный/слишком длинный финальный ответ отклоняется, не обрезается молча. Один пользовательский вопрос занимает один пункт пользовательской квоты и требует два модельных вызова минимум при штатной обработке; полный учебный ответ требует три. При transport/model/schema error цепочка может завершиться раньше. Кнопка полного retry доступна только для временной ошибки сервиса; лимиты и недостаток credits не предлагают немедленный retry. Чистить устаревшие записи лимитера и ограничить его 10 000 пользователями в UTC-день. Лимит хранится в памяти экземпляра и годится для закрытого прототипа, не для публичного платного сервиса. Ключи LLM держать только в серверном runtime.
- Для вызовов AI-конвейера отключить автоматические повторы (`maxRetries: 0`), чтобы число upstream-вызовов не росло незаметно. Каждый этап ограничить 30 секундами; успешный полный конвейер занимает до трёх запросов/примерно 90 секунд. При ручном повторе пользователь запускает всю цепочку сначала, до трёх дополнительных вызовов. Общий LLM helper сохраняет прежнее retry-поведение по умолчанию для других callers.
- Перед AI-вызовом сравнивать fingerprint всех входов симулятора с fingerprint сохранённого результата. Пока debounce-пересчёт не закончен, скрывать устаревшие траектории/доли исходов и отключать отправку; вопрос и сообщения пользователя допускают до 1 200 символов, финальный answer — до 5 000 без молчаливой обрезки.
- Отсутствующий URL/ключ проекта классифицируется как неисправимая runtime-конфигурация, не предлагает UI retry и проверяется до расхода per-user quota.
- В интерфейсе до отправки явно сообщать, что штатно каждый принятый запрос проходит минимум два вызова, полный успешный ответ требует три, а безопасный отказ возвращается после второго этапа; transport/model/schema error может оборвать цепочку раньше. Указывать увеличенные задержку и расход project credits; показывать схему этапов «разбор → проверка чисел риска → объяснение». Не имитировать прогресс отдельных этапов и не показывать их внутренние результаты. При ошибке сообщать, что точное число вызовов может быть неизвестно, а уже отправленные этапы могли списать credits. Ручной повтор должен явно сообщать, что запускает все этапы снова; кнопку показывать только для временной ошибки сервиса.
- Панель AI-командного центра добавляет вкладки «Команда», «Навыки» и «Команды»: роли являются человекочитаемым описанием тех же трёх последовательных стадий одной модели, навыки точно соответствуют серверному allow-list тем, а быстрые команды только запускают обычный образовательный вопрос после явного нажатия пользователя. Указывать возможные до трёх вызовов и расход project credits; не вводить скрытые/background вызовы, независимых несуществующих агентов, ложный поэтапный прогресс, новые источники рынка, реальные заявки или доступ к локальным данным.
- Доработанная визуализация связывает вопрос или быструю команду (отправляется как обычный запрос), шесть разрешённых серверным allow-list учебных тем, три последовательные стадии одной модели и сформированный сервером ответ в понятную статичную схему. Соединители показывают только структуру и порядок, не текущий прогресс; фактические итоги стадий появляются исключительно из серверной квитанции, во время запроса стадии не маркируются как активные или завершённые.
- Модель не обучается/не fine-tune: для отдельной модели позднее нужны отдельные данные, права и инфраструктура.

### Модули и структура

- `client/src/pages/Home.tsx`: текущий контекст и точка входа в AI-чат.
- `client/src/components/trader/ScenarioChart.tsx`: веер Monte Carlo с доступным выбором одной траектории, сбросом выделения при новом расчёте и явной маркировкой случайного учебного пути.
- `client/src/components/AIChatBox.tsx`: повторно использовать готовое безопасное отображение Markdown, loading и suggested prompts.
- `client/src/components/trader/TraderAIChat.tsx`: русскоязычный Skill Trader AI, сообщения, disclosure про три вызова, состояние pipeline, ошибки и ручной повтор.
- `client/src/components/trader/TraderAICommandCenter.tsx`: вкладки реальных ролей, allow-list учебных тем и ручных быстрых команд без фоновых модельных вызовов.
- `shared/traderAssistant.ts`: input schema, лимиты и публичные типы/метаданные трёх этапов; никакие свободные внутренние выводы не передаются клиенту.
- `server/routers.ts`: защищённый tRPC endpoint с Zod-валидацией и серверным лимитом; `server/_core/sdk.ts` подтверждает project-bound session JWT и создаёт минимальную сессию приложения без БД.
- `server/traderAssistant.ts`: system policy, строгие JSON-схемы трёх этапов, серверные intent/risk gates, сериализация истории как недоверенных данных, серверные расчёты, ограниченный final-output screen/fallback и in-memory rate limits.
- `server/_core/llm.ts`: `invokeLLM` с поддержкой ограниченного per-call `maxRetries`, сохранением прежнего значения по умолчанию и GPT `max_completion_tokens`; credentials никогда не отправляются в браузер.
- `server/*.test.ts`: mock-тесты проверяют порядок трёх этапов, JSON schema/payload, границы данных, остановку на некорректном output, отсутствие автоматического retry и максимум три model calls без платных model-запросов в unit suite.
- `README.md`, `TODO.md`, `docs/demo/`, `docs/trader-ai-model-notes.md`: ограничения, фактическое число вызовов, credits/latency, проверки и актуальные снимки.

## Однонаправленная инфраструктура

Владелец подтвердил включение server backend. Не включать Database и не запускать Publish; оставить `auto_publish=false`. Перед общедоступной публикацией отдельно добавить долговременное управление пользователями/ролями и распределённые ограничения API: stateless session role mapping и in-memory limiter сейчас рассчитаны только на закрытый прототип.

## Подготовка к релизу без публикации

Для production-зависимостей применяются только совместимые security overrides; обновления вне заявленных parent-диапазонов требуют отдельной проверки. Container liveness использует существующий публичный `/api/health`, но не подтверждает готовность OAuth или AI. Перед публичным запуском необходимо закрыть открытые release gates в `TODO.md`, включая повторное успешное CI и проверку реального container image; изменения кода и локальные сборки сами по себе не разрешают Publish.
